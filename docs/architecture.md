# Архитектура ШИБЕЙС

Документ для отчёта по работе 2.1. Описывает, из каких частей состоит система, как они связаны и почему.
Источник требований — [SPEC.md](SPEC.md), разделы 6–8 и 13; решения с альтернативами — [adr/](adr/).
Состояние на 2026-11-12: этап M0 завершён, существуют каркасы приложений с `/healthz`; остальное ниже —
проектное решение, которое реализуется на этапах M1–M10 ([PLAN.md](PLAN.md)).

## 1. Назначение

ШИБЕЙС — облачная платформа для студенческих проектных команд. Документы, доска и задачи хранятся в одном графе
знаний: объекты связаны между собой, ИИ строит из документов интеллект-карту и черновики задач, поиск работает
по всему пространству команды. Несколько человек редактируют документ или доску одновременно.

## 2. Схема

```
                ┌─────────────── Браузер ────────────────┐
                │ apps/web (React SPA)                    │
                │  ├─ BlockNote + Yjs ──┐                 │
                │  ├─ Доска (Konva)+Yjs ┼─ y-indexeddb    │
                │  └─ TanStack Query    │                 │
                └──────┬────────────────┼─────────────────┘
                REST + SSE│        WebSocket│(Yjs)
                ┌────────▼───┐   ┌────────▼────────┐
  Caddy (TLS) → │ apps/api   │   │ apps/collab     │
                │ Fastify    │   │ Hocuspocus      │
                └──┬───┬───┬─┘   └──┬──────────┬───┘
                   │   │   │        │          │ onStoreDocument →
                   │   │   └────────┼──────────┼──► Valkey (очереди BullMQ, pub/sub, кеш)
                   │   │            │          │          ▲
                   ▼   ▼            ▼          │          │
            PostgreSQL 17 + pgvector  ◄────────┘   ┌──────┴───────┐
            S3 (Yandex Object Storage / MinIO) ◄───│ apps/worker  │──► YandexGPT / GigaChat
                                                   │ импорт, ИИ,  │
                                                   │ индексация,  │
                                                   │ очистка      │
                                                   └──────────────┘
```

## 5. Два канала данных

Данные делятся на два вида, и у каждого свой путь.

**Содержимое страниц** (текст документа, элементы доски) живёт в Y.Doc. Клиент правит локальную копию, изменения
уходят по WebSocket в `collab`, тот рассылает их остальным и с задержкой 2–10 с сохраняет полное состояние в
`yjs_documents`. Локальная копия в IndexedDB позволяет работать при обрыве связи; слияние выполняет CRDT без участия
пользователя.

**Всё остальное** (аккаунты, пространства, дерево страниц, задачи, связи, файлы, запуски ИИ) — строки PostgreSQL,
доступные через REST. Об изменениях клиенты узнают из потока событий пространства (SSE) и обновляют кеш запросов.
Между процессами события передаются через pub/sub Valkey.

Производные данные — поисковый индекс и снимки версий — строятся на сервере из сохранённого Y.Doc: после сохранения
`collab` ставит задачу индексации с задержкой 15 с и дедупликацией по странице.

## 6. Ключевые потоки

**Открытие страницы.** Клиент запрашивает у API токен (`POST /collab/token`): JWT на 5 минут с идентификаторами
пользователя, страницы, пространства и ролью. С ним провайдер подключается к `collab`. Сервер проверяет подпись,
срок, соответствие имени документа `page.<pageId>`, актуальность членства и то, что страница не в архиве. Для роли
«читатель» соединение открывается только на чтение.

**Импорт файла.** Файл загружается в S3 через API, создаётся задача импорта. Воркер разбирает файл в блоки,
создаёт страницы и Y.Doc через `doc-model` и сообщает о ходе событиями `import.progress`.

**ИИ-структурирование.** API создаёт запуск и задачу в очереди. Воркер извлекает текст страниц, вызывает LLM через
`packages/ai`, объединяет понятия, раскладывает карту (`packages/layout`) и записывает результат на доску одной
транзакцией Y.Doc с меткой запуска — так его можно отменить целиком. Черновики задач создаются в PostgreSQL.

**Поиск.** Запрос выполняется в PostgreSQL двумя ветками — полнотекстовой с русской морфологией и векторной, —
результаты объединяются по RRF. Оба запроса ограничены пространством пользователя. Спайк M0.8 показал, что
векторную ветку в виде из раздела 10.3 нужно уточнить; это открытый вопрос ([STATUS.md](STATUS.md)).

## 7. Безопасность и права

- Одна функция `can(role, action, context)` в `packages/shared` реализует матрицу прав (Приложение E). Её
  используют и API, и `collab`; других проверок прав в коде нет.
- Сессии — в cookie, в БД хранится хеш идентификатора. Пароли — Argon2. Токены писем и приглашений хранятся хешами.
- Сервер совместного редактирования не доверяет клиенту: роль берётся из токена, выданного API.
- Данные пользователей размещаются в РФ; сторонние сервисы вне РФ для них не используются.
- Вызовы LLM идут к российским провайдерам; в разработке и тестах — только mock.

## 8. Развёртывание

| Окружение | Где                                           | Назначение                               |
| --------- | --------------------------------------------- | ---------------------------------------- |
| dev       | ноутбук или облачная среда разработки         | разработка, LLM — mock                   |
| ci        | GitHub Actions с сервисными контейнерами      | проверки                                 |
| staging   | ВМ Yandex Cloud, 2 vCPU / 4 ГБ                | приёмка, e2e, испытания функциональности |
| prod      | ВМ Yandex Cloud, 4 vCPU / 8–16 ГБ, SSD 100 ГБ | пилот, гостевой доступ, испытания KPI    |

Prod — одна ВМ с docker compose: Caddy (TLS, статические файлы `web`), `api`, `collab`, `worker`, PostgreSQL,
Valkey. Файлы — Yandex Object Storage. Резервные копии — ежедневный `pg_dump` с шифрованием в отдельный бакет и
еженедельная проверка восстановления. Обоснование и ограничения — [ADR 0008](adr/0008-hosting-yandex-cloud.md).

## 10. Что подтверждено на практике

Спайки этапа M0 ([tools/spikes/README.md](../tools/spikes/README.md)) проверили три самых рискованных места:

- BlockNote с Hocuspocus синхронизирует два клиента и сохраняет идентификаторы блоков при вставке;
- Konva держит доску из 2 000 элементов при отсечении невидимого и упрощённой отрисовке на мелком масштабе
  (замер без GPU, требует повтора на эталонном ноутбуке);
- гибридный поиск на 10 000 чанков отвечает за единицы миллисекунд, но векторная ветка с фильтром по пространству
  теряет кандидатов (замер на PostgreSQL 16 с pgvector 0.6, требует повтора на целевом образе).

Остальные свойства системы — нагрузка на сервер совместного редактирования, качество структурирования и поиска —
проверяются испытаниями на этапах M7–M10 и на момент написания не измерены.
