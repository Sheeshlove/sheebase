## M0.6. BlockNote + Hocuspocus

Версии: `@blocknote/core` и `@blocknote/server-util` 0.51.4, `@hocuspocus/server` и `provider` 3.4.4, `yjs` 13.6.33.
Сценарий: сервер Hocuspocus, два клиента с `HocuspocusProvider`, два редактора BlockNote поверх общего
`Y.XmlFragment` (в Node — через jsdom).

| Проверка                                                             | Результат                                |
| -------------------------------------------------------------------- | ---------------------------------------- |
| Два клиента подключаются и синхронизируются                          | да                                       |
| `server-util`: Markdown → блоки → Y.Doc                              | да, 6 блоков (заголовки, абзацы, список) |
| Второй клиент получает тот же документ с теми же id блоков           | да, доставка 25 мс на localhost          |
| id блоков из Markdown сохраняются при записи в Y.Doc                 | да                                       |
| Редактор, смонтированный поверх готового Y.Doc, не перегенерирует id | да                                       |
| Вставка блока в середину: старые id не меняются, новый id один       | да                                       |
| У второго клиента после вставки тот же порядок и те же id            | да                                       |
| Одновременная правка разных блоков сходится, id прежние              | да                                       |
| `server-util`: Y.Doc → Markdown                                      | да                                       |

Выводы для реализации:

- id блоков стабильны, их можно использовать как якоря ссылок и чанков поиска (`anchor_block_ids`).
- `server-util` тянет `jsdom` и `@blocknote/react` — это серверная зависимость `worker` и `api`, в бандл `web` не попадает.
- В Node нельзя подменять глобальные `Event` и `CustomEvent` классами jsdom: ломается встроенный `WebSocket`.
- Имя фрагмента в Y.Doc нужно зафиксировать одной константой в `packages/doc-model` (в спайке — `document-store`).

## M0.7. Konva, 2 000 элементов

Версия: `konva` 10.9.1. Сцена 1600×900, 2 000 стикеров (группа: прямоугольник со скруглением + текст) на поле
10000×6400, один слой без обработки событий. Камера двигается каждый кадр, кадр рисуется синхронно, время кадра —
интервал между `requestAnimationFrame`, 4 секунды на сценарий. Отрисовка программная (SwiftShader, GPU нет).

| Сценарий                              | Отсечение | Упрощение       | Элементов в кадре | Средний FPS | Кадр p95, мс |
| ------------------------------------- | --------- | --------------- | ----------------- | ----------- | ------------ |
| Панорамирование, масштаб 100 %        | нет       | нет             | 2000              | 14,0        | 116,7        |
| Панорамирование, масштаб 100 %        | да        | нет             | 56                | 60,0        | 16,8         |
| Масштаб 12 % ↔ 200 %                  | нет       | нет             | 2000              | 13,7        | 116,6        |
| Масштаб 12 % ↔ 200 %                  | да        | нет             | 92                | 56,3        | 16,8         |
| Обзор: всё поле в кадре, масштаб 16 % | да        | нет             | 1748              | 16,1        | 99,9         |
| Обзор: всё поле в кадре, масштаб 16 % | да        | да (без текста) | 1747              | 55,8        | 33,4         |

Выводы для реализации (M3.2):

- Без отсечения Konva не держит 2 000 элементов: 14 к/с. Отсечение невидимого обязательно, как и записано в NFR-PERF-4.
- Отсечение не помогает, когда вся доска в кадре. Там дорого стоит текст: без него 56 к/с вместо 16.
  Нужен уровень детализации — ниже порога масштаба рисовать плашки без текста. В ТЗ его нет, записано в допущения.
- Порог NFR-PERF-4 (≥ 50 к/с) в этой среде достигнут во всех сценариях только с обоими приёмами, причём в обзоре
  p95 кадра 33 мс — запас небольшой. Замер на эталонном ноутбуке с GPU обязателен до фиксации решения.
- Кеширование слоёв в спайке не проверялось.

## M0.8. pgvector HNSW + FTS `russian` + RRF

**Отклонение среды:** Docker недоступен, образ `pgvector/pgvector:pg17` запустить нельзя. Спайк выполнен на локальном
PostgreSQL 16.15 с pgvector 0.6.0 из пакетов Ubuntu. Собрать pgvector 0.8 из исходников не удалось: сетевая политика
среды не пропускает загрузку с GitHub. Замер на целевом образе нужно повторить (`pnpm infra:up`, затем та же команда).

Данные: 10 000 чанков в 10 пространствах по 1 000, синтетические русские тексты из собственного словаря,
mock-эмбеддинги 256 измерений (хеширование основ слов). Схема и запрос — по 7.1 и 10.3: `tsv` — генерируемый столбец
с весами A и B, индексы HNSW `vector_cosine_ops`, GIN и btree; запрос с `WHERE workspace_id = …`, RRF с k = 60.
200 запросов, половина — в словоформах, которых нет в текстах.

| Показатель                                      | Значение            |
| ----------------------------------------------- | ------------------- |
| Вставка 10 000 строк (пакеты по 500)            | 2,9 с               |
| Построение HNSW                                 | 1,7 с               |
| Построение GIN                                  | 0,04 с              |
| Размер таблицы / индексов                       | 21 МБ / 14 МБ       |
| FTS, top 50: p50 / p95                          | 2,2 / 3,4 мс        |
| Вектор через HNSW, `ef_search = 100`: p50 / p95 | 1,7 / 2,8 мс        |
| Гибридный запрос с RRF одним SQL: p50 / p95     | 3,7 / 5,1 мс        |
| FTS находит другие словоформы                   | 100 из 100 запросов |

Цель 10.3 по времени (p95 ≤ 700 мс) на этом объёме выполняется с запасом на два порядка.

**Найденная проблема.** HNSW применяет фильтр по `workspace_id` после обхода графа. При `ef_search = 100` и десяти
пространствах векторная ветка возвращает в среднем 9,8 строки из 50 запрошенных (минимум 4), полнота относительно
точного поиска — 0,20. Запрос из 10.3 в таком виде теряет большую часть векторных кандидатов, и чем больше пространств
в базе, тем сильнее.

| Вариант векторной ветки                          | Строк из 50 | Полнота | p50 / p95, мс |
| ------------------------------------------------ | ----------- | ------- | ------------- |
| HNSW, `ef_search = 100` (как в 10.3)             | 9,8         | 0,20    | 1,7 / 2,8     |
| HNSW, `ef_search = 1000` (максимум)              | 50          | 1,00    | 7,9 / 11,0    |
| Точный поиск: btree по пространству + сортировка | 50          | 1,00    | 2,7 / 3,9     |

Гибридный запрос с точной векторной веткой: p50 4,6 мс, p95 6,7 мс.

Варианты решения — выбор за человеком, до M8.1:

1. Точный поиск внутри пространства (без HNSW). На 1 000 чанков быстрее, чем HNSW с большим `ef_search`, и полнота 1,0.
   Время растёт линейно с размером пространства; где предел — нужно замерить на 10–50 тыс. чанков в одном пространстве.
2. `hnsw.iterative_scan` из pgvector 0.8 (в целевом образе он есть). В этой среде не проверен.
3. `ef_search = 1000` — помогает только пока пространств мало, не масштабируется.

Формально 6.2 выполнено: pgvector, HNSW, FTS `russian` и RRF работают. Но запрос 10.3 требует правки, поэтому
это вынесено в блокеры `docs/STATUS.md`.
